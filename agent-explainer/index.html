CHAPTER 00 · 一句话读懂 Agent

让大模型从「只会说」变成「能动手」

Agent（智能体）= LLM（大脑） + Planning（规划） + Memory（记忆） + Tools（手脚）， 再放进一个「思考 → 行动 → 观察 → 再思考」的循环里，直到目标达成。 LLM 是一个问答函数，Agent 是一台能自己跑完任务的机器。

01

为什么需要 Agent？——直击 LLM 的四大局限

裸用大模型就像请了一位博学的「顾问」——他什么都懂，但什么都干不了

🖐️

只会说不会做 No Action

模型能写出「如何调用退款接口」的代码，却没法真的去调那个接口。它没有手。

Agent 解法：挂载工具（Tool），模型输出结构化调用指令，由执行器真正落地
🐟

金鱼记忆 No Memory

每一轮对话都从零开始。上一轮查到的订单号，下一轮它已经忘了。

Agent 解法：短期缓冲 + 长期向量记忆 + 工作记忆三层结构，跨轮次保持状态
🎯

单步思维 No Planning

让它「做一份竞品分析」，它一口气吐出一段文字，不会拆成「找资料 → 拉数据 → 做对比 → 写结论」。

Agent 解法：规划器把大目标拆成子任务序列，一步步执行并动态修正
🔌

系统孤岛 No Connection

你的 CRM、数据库、工单系统、内部 API，模型一个都进不去。

Agent 解法：标准化工具协议（Function Calling / MCP）把企业系统接成大模型的手脚
02

Agent 到底是什么？

一个公式 + 一个比喻，三分钟讲透

核心公式
Agent = LLM + Tools + Memory + Planning

并且这个组合被放进一个循环：思考 → 行动 → 观察 → 再思考，直到目标达成才停止

🧑‍💼

一个比喻：从「顾问」到「实习生」

  • LLM 大脑 = 实习生的知识水平与判断力
  • 工具 Tools = 他能用的电脑、电话、系统账号
  • 记忆 Memory = 他的记事本和你的历史交办
  • 规划 Planning = 他接到任务后先列 TODO 再动手
  • 护栏 Guardrails = 报销超过 5000 元必须找你签字
没有 Agent 的 LLM = 一个只能口头回答问题的顾问，永远不动手

进阶 Agent · 从单次调用到自主协作

四层进化路径 · 自主性越高，能力越强，也越难控

L1

工具调用

Function Calling：一问一答中夹带一次工具调用，没有循环

  • 单轮：问 → 调工具 → 答
  • 无记忆、无规划
  • 适合简单查询类场景
L2

ReAct 循环

推理与行动交替进行，边做边看，直到达成目标

  • Thought → Action → Observation 循环
  • 能处理多步骤任务
  • 工业界最主流的范式
L3

规划式 Agent

先出完整计划再执行，失败后重新规划或自我反思

  • Plan-and-Execute 两段式
  • Reflexion 引入失败复盘
  • 长任务更稳、更省 token
L4

多智能体协作

多个专业 Agent 分工协作，有调度者也有执行者

  • Manager-Worker 架构
  • 角色分工 + 结果互审
  • 复杂项目级任务
🔁

ReAct（Reasoning + Acting）

让模型在每一步先输出一段思考，再决定调用哪个工具，拿到结果后继续思考。把「想」和「做」交错起来，是当前最通用的 Agent 骨架。

Thought → Action → Observation → Thought → ... → Answer
📋

Plan-and-Execute

先用强模型做一次完整的任务规划，再逐步执行。适合步骤明确的长任务，token 消耗更低，但计划一旦错了整条链路都会偏。

目标 → 完整计划 → [Step1, Step2, ...] → 顺序执行
🪞

Reflexion（自我反思）

任务失败后不让它直接重试，而是先写一段「为什么失败」的复盘，把教训写进记忆再重来。类似人类的「吃一堑长一智」。

失败 → 复盘失败原因 → 写入记忆 → 重试
👥

Multi-Agent（多智能体）

一个主管 Agent 拆解任务，分给多个专业 Agent 并行执行，最后汇总审核。适合一个人干不完或需要交叉校验的复杂任务。

Manager → [Researcher, Coder, Critic] → 汇总
🧑‍💻

Human-in-the-loop

在关键节点插入人工确认。不是所有动作都能交给机器，涉及真金白银或不可逆操作时，必须有人按下确认键。

高危动作 → 暂停 → 人工确认 → 继续
🖥️

Computer / Browser Use

让 Agent 直接操作浏览器和桌面：点击、输入、截图识别。不需要对方提供 API，代价是稳定性差、速度慢。

截图 → 视觉理解 → 点击/输入 → 校验

"""
极简版 Agent · 不依赖任何 Agent 框架，80 行讲透 ReAct 原理
"""
import json
from openai import OpenAI

client = OpenAI()

# ---------- 1. 工具定义 ----------
def get_weather(city: str) -> str:
    """查询城市天气（示例：真实场景换成 API 调用）"""
    fake_db = {"北京": "晴 26°C", "上海": "小雨 23°C"}
    return fake_db.get(city, "暂无该城市数据")

def search_flights(from_city: str, to_city: str, date: str) -> str:
    """查询航班（示例）"""
    return f"{date} {from_city}→{to_city}：CA1234 08:00 / MU5678 14:30"

# 工具名 → 函数 的映射表，Agent 决定调用后由它真正执行
TOOLS = {"get_weather": get_weather, "search_flights": search_flights}

# 工具的 JSON Schema（给模型看的"说明书"）
TOOL_SCHEMA = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询指定城市的当前天气。当用户问天气、是否需要带伞时使用。",
            "parameters": {
                "type": "object",
                "properties": {"city": {"type": "string", "description": "城市名，如 北京"}},
                "required": ["city"],
            },
        },
    },
    {
        "type": "function",
        "function": {
            "name": "search_flights",
            "description": "查询两个城市之间指定日期的航班列表。",
            "parameters": {
                "type": "object",
                "properties": {
                    "from_city": {"type": "string"},
                    "to_city": {"type": "string"},
                    "date": {"type": "string", "description": "格式 YYYY-MM-DD"},
                },
                "required": ["from_city", "to_city", "date"],
            },
        },
    },
]

SYSTEM_PROMPT = """你是一个出行助理。你可以调用工具来获取实时信息。
规则：
1. 需要实时数据时必须调用工具，不要凭记忆编造
2. 每次只调用必要的工具，拿到结果后再决定下一步
3. 信息足够时直接给出结论，不要画蛇添足
"""

# ---------- 2. ReAct 主循环 ----------
def run_agent(user_task: str, max_steps: int = 8):
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": user_task},
    ]
    trace = []

    for step in range(max_steps):          # ← 刹车：最多循环 8 步
        resp = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=messages,
            tools=TOOL_SCHEMA,
            temperature=0.2,
        )
        msg = resp.choices[0].message
        messages.append(msg)                # ← 思考结果回填上下文

        # 没有工具调用 → 认为任务完成，输出最终答案
        if not msg.tool_calls:
            return msg.content, trace

        # 有工具调用 → 逐个执行，把结果作为 Observation 回填
        for call in msg.tool_calls:
            name = call.function.name
            args = json.loads(call.function.arguments)
            trace.append({"step": step + 1, "action": name, "args": args})

            try:
                result = TOOLS[name](**args)        # ← 真正执行
            except Exception as e:
                result = f"工具执行失败：{e}，请调整参数或换用其他工具"   # ← 错误也回填

            trace[-1]["observation"] = result
            messages.append({
                "role": "tool",
                "tool_call_id": call.id,
                "content": str(result),
            })

    return "已达最大步数仍未完成，请人工介入", trace   # ← 兜底

# ---------- 3. 运行 ----------
answer, trace = run_agent("我明天要去上海出差，帮我看下天气和航班")
for t in trace:
    print(f"[Step {t['step']}] 调用 {t['action']}({t['args']}) → {t['observation'][:40]}")
print("\n最终答案：", answer)

"""
LangChain 版 Agent · 用现成框架少写一半代码
前置：pip install langchain langchain-openai
"""
from langchain.agents import AgentExecutor, create_tool_calling_agent
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.tools import tool
from langchain_openai import ChatOpenAI
from langchain_community.chat_message_histories import ChatMessageHistory

# ---------- 1. 定义工具（用装饰器，函数注释就是给模型看的描述）----------
@tool
def search_docs(query: str) -> str:
    """在企业知识库中检索资料。当问题涉及公司内部制度、产品参数时使用。"""
    return f"[检索结果] 关于「{query}」的 3 条相关文档……"

@tool
def query_database(sql: str) -> str:
    """对只读数据仓库执行 SQL 查询。只允许 SELECT 语句。"""
    if not sql.strip().lower().startswith("select"):
        return "错误：只允许 SELECT 查询"
    return f"[查询结果] 执行 {sql[:50]}... 返回 128 行"

@tool
def send_notification(channel: str, message: str) -> str:
    """向指定渠道发送通知消息。channel 可选：dingtalk / email / sms"""
    return f"已通过 {channel} 发送：{message[:30]}"

tools = [search_docs, query_database, send_notification]

# ---------- 2. 提示词（必须保留 agent_scratchpad 占位符，这是 ReAct 的记忆区）----------
prompt = ChatPromptTemplate.from_messages([
    ("system", """你是一个企业运营助理。
工作原则：
- 需要事实数据时先调工具，不要凭空回答
- 涉及发送消息等外部动作前，先确认内容无误
- 完成后用简洁的中文汇报结果，附上关键数据"""),
    MessagesPlaceholder("chat_history", optional=True),   # 长期记忆挂载点
    ("human", "{input}"),
    MessagesPlaceholder("agent_scratchpad"),              # 中间步骤草稿区
])

# ---------- 3. 组装 Agent ----------
llm = ChatOpenAI(model="gpt-4o", temperature=0.2)
agent = create_tool_calling_agent(llm, tools, prompt)

# 护栏：最多 10 步、单次执行超时 60 秒、出错就停
executor = AgentExecutor(
    agent=agent,
    tools=tools,
    max_iterations=10,
    max_execution_time=60,
    handle_parsing_errors=True,
    return_intermediate_steps=True,   # 保留 Trace 用于排查
    verbose=True,
)

# ---------- 4. 带记忆地运行 ----------
history = ChatMessageHistory()

def chat(user_input: str):
    result = executor.invoke({"input": user_input, "chat_history": history.messages})
    history.add_user_message(user_input)
    history.add_ai_message(result["output"])
    return result

r = chat("帮我查一下最新的差旅报销标准，然后把结论发给财务群")
print(r["output"])
print(f"\n本次共执行 {len(r['intermediate_steps'])} 步工具调用")

"""
LangGraph 版 · 显式状态机 + 人工确认中断（生产级骨架）
前置：pip install langgraph langchain-openai
"""
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import MemorySaver
from langgraph.prebuilt import ToolNode, tools_condition
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool

# ---------- 1. 工具：区分只读与高危 ----------
@tool
def read_logs(service: str, minutes: int) -> str:
    """读取指定服务最近 N 分钟的日志摘要。"""
    return f"[{service}] 最近 {minutes} 分钟：502 错误 1243 次，集中在 14:02-14:07"

@tool
def restart_service(service: str, confirm: str) -> str:
    """【高危】重启线上服务。调用前必须获得人工确认。"""
    if confirm != "YES":
        return "已拒绝：缺少人工确认标记"
    return f"服务 {service} 已重启，实例数 3/3 健康"

@tool
def create_report(title: str, content: str) -> str:
    """生成故障报告文档。"""
    return f"报告《{title}》已生成，共 {len(content)} 字"

tools = [read_logs, restart_service, create_report]

# ---------- 2. 定义状态（Agent 的记忆与上下文）----------
class AgentState(TypedDict):
    messages: Annotated[list, add_messages]   # 消息历史自动累加
    step_count: int                            # 已执行步数（用于刹车）

# ---------- 3. 节点：模型推理 ----------
llm = ChatOpenAI(model="gpt-4o", temperature=0).bind_tools(tools)

def agent_node(state: AgentState):
    if state.get("step_count", 0) >= 12:       # ← 硬性刹车
        return {"messages": [("assistant", "已达最大步数，停止执行并请求人工介入")]}
    resp = llm.invoke(state["messages"])
    return {"messages": [resp], "step_count": state.get("step_count", 0) + 1}

# ---------- 4. 组装图 ----------
graph = StateGraph(AgentState)
graph.add_node("agent", agent_node)
graph.add_node("tools", ToolNode(tools))
graph.set_entry_point("agent")

# 条件边：模型要调工具就去 tools，否则结束
graph.add_conditional_edges("agent", tools_condition, {"tools": "tools", END: END})
graph.add_edge("tools", "agent")               # ← 关键：工具执行完回到 agent，形成循环

# checkpoint 让中断/恢复成为可能
app = graph.compile(
    checkpointer=MemorySaver(),
    interrupt_before=["tools"],                # ← 调工具前暂停，等待人工批准
)

# ---------- 5. 运行 + 人工确认 ----------
config = {"configurable": {"thread_id": "incident-20260914"}}
state = app.invoke(
    {"messages": [("user", "订单服务 502 暴增，先看日志，如果确认是内存泄漏就重启它，最后出报告")]},
    config,
)

# 暂停在工具调用前，人工审核后继续
if state.get("__interrupt__"):
    print("⚠️ 即将执行高危操作，请审核：", state["__interrupt__"])
    if input("是否批准？(y/n) ").lower() == "y":
        state = app.invoke(None, config)        # 恢复执行

print(state["messages"][-1].content)

🎯

Task Success Rate 任务成功率

在一批真实任务上，Agent 端到端跑通的占比是多少？

目标：> 0.8（简单任务 > 0.95）

Step Efficiency 步数效率

完成同一任务，Agent 实际走了几步 vs 理论最优几步？

目标：实际步数 / 最优步数 < 1.5
🔧

Tool Accuracy 工具调用准确率

该调的时候调了吗？参数传对了吗？有没有调用不该调的工具？

目标：> 0.9（参数正确率单独看）
💰

Cost per Task 单任务成本

平均每个任务花多少 token / 多少钱？比人工便宜多少？

目标：低于人工成本的 1/5

📈 优化方向 · 当指标不达标时，从哪里下手？

成功率低

→ 补 Few-shot 示例 / 换更强模型做规划节点 / 拆分任务粒度 / 增加工具覆盖面

步数太多

→ 优化工具描述减少试错 / 加 Plan 前置规划 / 合并可并行的工具调用 / 缓存中间结果

工具调错

→ 重写工具描述与参数 Schema / 减少同类工具数量 / 加参数校验与友好报错

成本过高

→ 小模型跑简单步骤 / 压缩 Observation / 缩短记忆注入 / 提高缓存命中率

08

生产实践 · 踩过的坑和最佳实践

从 Demo 到生产，需要跨越的 6 道坎

01

工具描述决定调用准确率

90% 的工具调用错误源于描述含糊。写清「什么时候用、参数怎么填、什么情况不要用」，比换模型更有效。

02

每一步都必须可观测

完整记录 Thought / Action / Observation / 耗时 / token。Agent 出问题时，Trace 是唯一能复盘的证据链。

03

循环必须有刹车

最大步数 + 超时 + 成本上限三重熔断。没有刹车的 Agent 一旦陷入循环，会在几分钟内烧掉一天的预算。

04

写操作要幂等 + 可回滚

任何会改数据的动作都要带幂等键，失败重试不能造成重复扣款。不可逆操作前强制人工确认。

05

代码执行必须沙箱隔离

Agent 生成的代码要在无网络或白名单网络的容器里跑，限制 CPU/内存/时长，绝不能直接在生产机器上执行。

06

先做窄场景，再做通用

不要一上来就做「万能助理」。先在一个高频、边界清晰、可衡量的场景做到 90% 成功率，再横向扩展。
